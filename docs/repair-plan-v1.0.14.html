03CriticalStop false-success savesComplete locally

Save reliability is verified locally. Writes require returned record confirmation before state or success activity changes. Errors retain prior state and offer Retry; secondary failures retain confirmed saves and show a distinct warning. Real database/RLS acceptance remains part of the release gate.

What to do

  1. 1

    Check every Supabase response for errors and confirm the expected record was affected.

    Primary inserts, updates, upserts and deletes check errors and returned identities. Required refresh reads also check errors. Optional activity failures are shown as synchronization warnings.

    Complete
  2. 2

    Update client state after persistence, or add rollback for deliberate optimistic updates.

    Confirmed returned values update client state. Denied, network and zero-row results preserve it. Functional override merges and parent-only deletion also repair adjacent C5/C8 regressions.

    Complete
  3. 3

    Add visible errors and retry controls; prevent repeated clicks while pending.

    Shared inline errors and Retry are available in the app and dialogs. Pending saves disable affected controls; duplicate saves are rejected visibly. Notes/score failures retain the draft. Batch retry targets only failed IDs.

    Complete
  4. 4

    Separate a successful mutation from a failed subsequent refresh.

    Create/edit/delete refresh in the background. A committed write remains successful if history, activity or refresh fails; warnings offer read-only refresh rather than repeating the mutation.

    Complete

How we verify it

  • Permission, network and missing-record failures never show Saved.
  • Denied writes preserve prior client state.
  • Reloaded state agrees with the save result.
